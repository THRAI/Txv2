# Decision: v3 TDD migration baseline lock

**Date:** 2026-05-09

## Decision

- The v3 TDD migration plan ([`docs/progress/plans/2026-05-09-v3-tdd-migration.md`](../plans/2026-05-09-v3-tdd-migration.md)) requires a frozen test baseline so per-PR deltas are reviewable. The baseline at the head of this branch (PR-0 base) is recorded below. Every subsequent v3 migration PR must hold or grow these counts.

## Context

- v3 migration touches 354 production sites across 75 files for the `StepOutcome` 5→4 collapse alone (plan §4, doc 07 §3). With that many mechanical edits across ~14 worker-partitioned commits, drift is the chief risk.
- A single locked baseline is the cheapest way to detect a worker accidentally regressing tests outside its scope.
- The baseline is per-aggregate. Per-binary deltas will be enumerated in the wave landing notes if needed.

## Consequences

- Every v3 migration PR description includes a one-line baseline diff: e.g. "tests: 1152 → 1156 (+4 new test cases, 0 regressions)".
- A worker reporting "my crate is green" without confirming the workspace count is no-op is treated as an incomplete handoff; main-agent integration re-runs the full suite before stacking the next worker's commit.
- Net new tests added by PR-0 (proptest monoid laws + classify matrix + exhaustive-match smoke in `crates/tx-substrate/tests/v3_algebra.rs`) are added on top of this baseline; PR-0 lands at 1152 + N.

## Alternatives Considered

- **Per-crate baselines.** Rejected: cross-crate refactors (e.g. W-shims-fs depending on W-vfs+W-page-backed) make per-crate locks misleading. Workspace-aggregate is the correct unit because it's what `cargo test --workspace` actually checks.
- **No baseline lock; trust CI.** Rejected: there is no remote CI yet on this repo, and the migration's blast radius is too large for ad-hoc per-PR comparison. A frozen number in source-controlled docs is the simplest contract.
