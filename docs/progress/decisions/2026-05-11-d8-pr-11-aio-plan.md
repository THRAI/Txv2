## 1. What is Linux AIO?

Linux POSIX AIO (`io_setup(2)`, `io_submit(2)`, `io_getevents(2)`,
`io_destroy(2)`) is the **kernel-mediated asynchronous I/O** family
that pre-dates `io_uring`. A submitting task calls `io_setup(nr_events,
&aio_context_t)` to allocate a per-process **AIO context** (a queue
of `nr_events` slots backed by kernel memory plus a user-visible ring
buffer, identified by an opaque `aio_context_t` — a `u64`-pointer
value, **not a fd** in mainline Linux). The task then calls
`io_submit(ctx, n, struct iocb *iocbpp[])` with an array of I/O
control blocks (`struct iocb { aio_fildes, aio_lio_opcode (PREAD /
PWRITE / FSYNC / …), aio_buf, aio_nbytes, aio_offset, … }`); the
kernel attaches each iocb to a worker (the historical "AIO kthread"
or, in newer kernels, the workqueue), the worker performs the I/O
asynchronously, and on completion posts a `struct io_event` into
the context's completion ring. The submitter retrieves completions
via `io_getevents(ctx, min, max, events, timeout)` and tears the
context down with `io_destroy(ctx)`. Linux's AIO is **direct-I/O
only** in spec; glibc emulates buffered AIO with userspace threads.

The structural fact: **the submitter and the I/O executor are
different tasks, but the executor's permission checks, file table
lookups, address-space access, and rlimit charges all resolve
against the submitter's identity.** That is exactly the
`OnBehalfOf<P>` shape from `06_EXECUTION_SCOPE_v1.md`.

## 2. Why is AIO the `OnBehalfOf<P>` canary?

Map AIO primitives onto the execution-scope concepts from
`06_EXECUTION_SCOPE_v1.md`:

| AIO primitive | `OnBehalfOf<P>` concept |
|---|---|
| Submitting task (caller of `io_submit`) | The **principal P** — `Cap<ProcessIdentity>` |
| Per-submission `struct iocb` | A unit of work to perform under P's `SubjectContext::borrowed(P, …)` |
| Kernel AIO worker (kthread / workqueue) | The kernel actor whose own thread identity does the scheduling, but whose **`SubjectContext.authority` is derived from P** for every permission check, file lookup, rlimit charge |
| `aio_fildes` lookup | Resolves against **P's fd table** (not the worker's — the worker has none in the user-fd sense) |
| `aio_buf` user-pointer copy-in / copy-out | Resolves against **P's address space** — the worker reads / writes P's user memory under the borrow |
| Completion ring write-back | A `WakeHint`-style wake routed back to **P's `TaskMailbox`** (or a per-AIO-context mailbox tied to P) |
| `io_destroy` / P exit | Drops the borrow → in-flight workers see scope abandonment via `exit_source` → unfinished iocbs reach `EOWNERDEAD` |
| `io_cancel(ctx, iocb, result)` | Cancels one in-flight iocb; needs cooperative abort from the worker's borrow-scope drive loop |

**Contrast with PR-10 (OnAgent).** PR-10's userfaultfd has the
**agent answering a kernel question**: the faulting thread *is* P,
and the agent has *its own, different* `SubjectContext`. There is
no identity borrow; the agent is just a userspace process the
kernel converses with through the ufd. PR-11's AIO is **the inverse
direction**: a kernel actor (not a user agent) does kernel work
**as if it were P**. The agent answers a question; the worker
borrows an identity. These are not variations of the same
primitive — they are orthogonal axes of the script-context lattice.

This is also why D7's "subject" of the script (the faulting
thread) keeps its own thread identity, while D8's worker explicitly
sets `SubjectContext.thread = None` per
`06_EXECUTION_SCOPE_v1.md` §4 (`SubjectContext::borrowed` —
already declared at `crates/tx-substrate/src/step_v3/subject_context.rs:356`).

## 3. Substrate readiness audit — what's net-new?

### 3.1 `ExecutionScope::OnBehalfOf` catalog member — placeholder-only

Grep evidence at
`crates/tx-substrate/src/step_v3/execution_scope.rs:46-55`:

```rust
pub enum ExecutionScope {
    Thread,
    OnBehalfOf(OwnedProcessHandle),    // ← placeholder, _private: ()
}
```

`OwnedProcessHandle` is a unit-typed placeholder (lines 27-37).
The closed catalog is declared but the borrow primitive is
**explicitly deferred to PR-7** per the doctext:

> "Wave 3 of the v3 TDD migration plan lands the closed catalog +
> helper methods only; the borrow primitive (`with_on_behalf_of`
> async fn), abandonment routing through `Killable`, and
> resource-scoping discipline are deferred to PR-7."

PR-7 landed only the **OnAgent** runtime (delegate state machine
+ mailbox routing). The `OnBehalfOf` runtime did *not* land in
PR-7. PR-11 must populate it.

**Net-new in PR-11:**

- Replace `OwnedProcessHandle { _private: () }` with the real
  `Cap<I>`-bearing variant: `ExecutionScope::OnBehalfOf(Cap<I>)`
  generic over `I: SubjectIdentity`.
- Add the `with_on_behalf_of<I, F, R>` async helper per
  `06_EXECUTION_SCOPE_v1.md` §3, returning a borrow-scope guard
  that owns the cap clone, subscribes the owner's `exit_source`,
  and routes abandonment.

### 3.2 Subject-borrow mechanism — `SubjectContext::borrowed` exists

`SubjectContext::borrowed(process: Cap<I>, authority: SubjectAuthority<I>)`
is **already declared** at
`crates/tx-substrate/src/step_v3/subject_context.rs:356`. The
constructor pre-dates PR-11; it was added in PR-9 phase 4
alongside `from_thread` for the explicit purpose of supporting
this `OnBehalfOf<P>` case (the SUBJ-2(b) shape). The worker's
borrow body receives a `SubjectContext<I>` where:

- `process = owner.clone()` (the principal P)
- `thread = None` (the worker has no user-thread identity)
- `authority = SubjectAuthority::derived_from(owner)` — a snapshot
  of P's `Cap<Cred>` and `Cap<Restrictions>` (per D5, both are
  cap-shaped and cheap to clone)

**Net-new in PR-11:**

- A `SubjectAuthority::derived_from(owner: &Cap<I>) -> SubjectAuthority<I>`
  constructor that materializes the snapshot. Today's
  `SubjectAuthority::new(cred, restrictions)` requires the caller
  to source caps explicitly; the `derived_from` helper reads
  `owner.cred_cap()` / `owner.restrictions_cap()` (the latter
  through the trait — `ProcessIdentity::restrictions_cap`
  accessor must exist; if not, a small additive helper).

### 3.3 Restriction-stack propagation — works in-place per D5

Per D5 Path A: `Cap<Cred>` is the cred handle, and the eventual
real restrictions-stack adopts the same swap shape. The borrow's
`SubjectAuthority` snapshots **the caps at borrow time** (per
`06_EXECUTION_SCOPE_v1.md` §4: "borrowed authority is a snapshot
at borrow time"). If P does a `setuid` mid-borrow, the borrow
keeps the **old** caps until the borrow drops — exactly the
Linux AIO behavior (an iocb in flight when the submitter
`setuid`s is checked against the cred the submitter had at submit
time, modulo POSIX corner cases that v1 does not aim to match
bit-for-bit). The cap-clone semantics give this **for free**:
the old `Cap<Cred>` keeps the old slot alive via EBR; the new
`Cap<Cred>` in P's slot is the post-mutation cred, but the
worker's borrow holds the pre-mutation cap.

**No substrate change needed.** The capability-snapshot semantics
already encode the "stable for borrow duration" rule of
`06_EXECUTION_SCOPE_v1.md` §4.

### 3.4 Permission-check discipline — `SyscallCtx` reads from `SubjectContext`, not the worker

This is the load-bearing discipline: every authority check inside
the worker's borrow body must read the **borrow's** `SubjectContext`,
not the worker thread's own task. Today's `SyscallCtx<'a>` in
`tx-shims/src/linux_syscall/mod.rs` materializes `SubjectContext`
from the calling thread (PR-9 phase 5, per D5 §6.1 item 10). For
the worker case, the script body must be invoked with a
`ScriptCtx<I>` whose `subject` is the **borrowed** context, not the
worker's own.

The mechanism is straightforward: `with_on_behalf_of` constructs a
fresh `ScriptCtx<I>` for the body's duration, with
`script_ctx.subject = SubjectContext::borrowed(owner, authority)`.
Step bodies inside the body only ever receive `&ScriptCtx` (or
`&SubjectContext`) per SUBJ-1 — they cannot read a "current thread"
without an explicit accessor (deliberately absent). The discipline
holds **by absence**.

**Net-new in PR-11:**

- The async-helper boilerplate that swaps the worker thread's
  `ScriptCtx` to the borrow's `ScriptCtx` for the body's duration.
  This is mostly a builder pattern around `SubjectContext::borrowed`
  + a way for the AIO subsystem's worker `async fn` to consume it.

### 3.5 Per-syscall write-back — wake P's `TaskMailbox`

When the worker finishes an iocb, the completion event must land
**on P's view** — specifically on the AIO context's completion
ring (which lives in P's address space) and notify P's mailbox so
a pending `io_getevents` wakes. The `TaskMailbox` substrate from
PR-7B already routes `MailboxEvent::AgentReplied { token_id }`
across task boundaries via `Weak<TaskMailbox>`. PR-11 reuses this
pattern but with a **different event variant** — call it
`MailboxEvent::AioCompletion { iocb_id }` or, more cleanly, a new
`WakeHint::AioCompletion` variant carried over the existing wake
infrastructure.

The completion-ring write itself is a `copy_to_user` against P's
address space; the worker performs it under the borrow's
`SubjectContext`, so the existing user-access discipline applies
unchanged (the user pointer is validated against P's address-space,
not the worker's).

**Net-new in PR-11:**

- One `MailboxEvent` / `WakeHint` variant for AIO completions
  (~10 LoC + matching driver-side consumer).

### 3.6 Cancellation — interacts with the borrow's `exit_source`, not `AgentTokenGuard`

PR-7's `AgentTokenGuard` is the **OnAgent** RAII guard for in-flight
delegations; it owns a `DelegateTokenId` and cancels the agent's
pending work on drop. AIO cancellation is different in three ways:

1. The "thing being cancelled" is a worker's in-progress I/O
   syscall, **not** a delegated request to a user agent.
2. The cancel signal comes from `io_cancel(iocb)` (an explicit
   syscall) or from P's exit (abandonment).
3. The worker must observe the cancel cooperatively — the I/O op
   itself (`step_pread`, `step_pwrite`) must yield often enough
   for a `WaitProtocol`-driven abort to land.

The mechanism per `06_EXECUTION_SCOPE_v1.md` §5: the borrow scope
subscribes the owner's `exit_source` as a `Killable` wait source.
On P's exit or `io_destroy`, the source fires, the body's drive
loop observes a `Killed` outcome on its next yield resolution, and
the worker's iocb completes with `EOWNERDEAD`. For `io_cancel(iocb)`,
the AIO subsystem maintains its own per-iocb cancel source
(another `WaitSource`) and posts a "cancel this iocb" event.

**Net-new in PR-11:**

- A per-AIO-context (or per-iocb) `WaitSource` for cancellation
  signaling, plumbed into the borrow-body's drive loop.
- The borrow-scope abandonment routing: `exit_source` subscription
  + `Killable`-protocol consumer.

### 3.7 Worker scheduling — reactor task is the worker

PR-7's runtime uses the **reactor** to drive scripts. A kthread is
just a reactor task with no user-thread backing. AIO workers are
therefore reactor tasks spawned by `io_setup` that hold the
`OnBehalfOf<P>` scope for their lifetime. The worker pool model
(one task per iocb, or a small pool serving iocbs from a queue) is
a subsystem choice — the substrate doesn't impose either.

**Decision for PR-11:** one reactor task per AIO context (the
worker). Inside that task, iocbs are processed sequentially under
a single long-lived borrow. This matches
`06_EXECUTION_SCOPE_v1.md` §6 ("long-lived resources require a
long-lived scope") and is the smallest viable shape.

**No substrate change needed.** The reactor's task spawn surface
is sufficient.

## 4. AIO-side gap audit

### 4.1 `aio_context_t` — fd or pointer?

Linux's `aio_context_t` is **not a fd**. `io_setup` returns it as an
opaque pointer-shaped value through a userspace `aio_context_t *ctxp`
out-parameter; later syscalls accept it by value, not as a file
descriptor. The kernel implementation backs it with a memory region
mapped into the caller's address space (the ring buffer); the
"context id" is essentially the user-virtual address of that
region.

**Decision: normalize to a fd-shaped handle for this kernel.** PR-10
already taught the OpenFile system to admit non-VFS backings via
`OpenFileBacking { Rnode(...), Ufd(...) }` (STATUS 2026-05-11
PR-10 phase 0). Adding a third variant
`OpenFileBacking::AioContext(Cap<AioContext>)` is mechanically
identical to PR-10's `Ufd` variant landing. The user-visible
contract diverges from Linux (we hand back a real `fd` from
`io_setup` instead of a pointer-shaped `aio_context_t`), but the
divergence is small, the implementation is uniform with ufd, and
**`io_destroy` becomes structurally identical to `close(2)`**
(cap-zone drop drives endpoint abandonment via the same
`exit_source` mechanism). Userspace AIO wrappers that bridge
glibc `io_setup` to our fd-based call site need one trivial shim
(treat the returned `aio_context_t` as a numeric fd value).

Future flex: this fd-shape is the same shape io_uring uses in
Linux (`io_uring_setup` returns a fd; SQEs/CQEs are mmapped off
that fd). A future SQPOLL/io_uring landing reuses this discipline
verbatim. **The fd-shape decision unifies AIO and io_uring under
one fd-backing-zone discipline.**

### 4.2 Request queue + completion queue

Linux maps the iocb ring + completion ring into the caller's
address space. Our model uses:

- **Submission queue:** kernel-side `MpscQueue<IocbCap>` inside
  the `AioContext` zone payload. `io_submit` does
  `copy_from_user(iocb_array)`, parses each into `IocbCap`,
  enqueues. **No user-mmapped submission queue in PR-11** — the
  syscall is the only producer.
- **Completion queue:** *user-mmapped ring buffer in P's address
  space*, written by the worker via the borrow's `copy_to_user`.
  This matches Linux's `io_getevents` semantics; userspace can
  poll the ring directly for completed events, and
  `io_getevents` is a fast-path for the no-events-yet wait.

Trade-off: a kernel-side completion list (instead of user-mmapped
ring) would be simpler but loses the io_getevents-bypass property.
The user-mmapped ring is small and mirrors Linux closely enough
that future AIO conformance tests will pass.

### 4.3 Direct-I/O only?

Linux AIO is `O_DIRECT` only for guaranteed-async behavior;
buffered AIO under Linux silently degrades to synchronous
in-syscall I/O for cached pages. **For PR-11 we admit both** but
the canary phase ships **buffered `pread`** as the smallest
viable op. Direct-I/O requires a `O_DIRECT` open mode our VFS
doesn't yet honor (page cache always interposes); admitting the
flag and short-circuiting to a direct-fs path is its own work
(out of PR-11 scope). Buffered AIO is still asynchronous in our
model because the worker is a separate reactor task — the
"silent degradation" of Linux doesn't apply because we never
held the syscall context.

**Decision: buffered AIO via the existing `step_read`/`step_pread`
VFS path, executed under the worker's borrow.** Direct-I/O is a
follow-up PR-11.1.

with three small substrate edits (D7 §4). PR-11 is the opposite:
the `OnBehalfOf<P>` framework is **net-new per
`07_BLAST_RADIUS.md` §4 row J** (~500 LoC, "defers cleanly
until first user materializes"). Two phases of PR-11 (P-11.0,
P-11.1) build the framework; the remaining six (P-11.2 through
P-11.7) build AIO on top.

Quantitatively, PR-11 is therefore **"PR-10's level of effort
plus the ~500-LoC framework"** — but D5 + PR-10 phase 0 have
already done some of that framework work (the `SubjectContext::borrowed`
constructor in PR-9 phase 4, the `OpenFileBacking` enum in PR-10
phase 0, the cap-shaped cred/restrictions in D5). Net result:
PR-11's estimate (5–6 days) is **at the bottom of the
BLAST_RADIUS budget**, not the middle — the rolling substrate
work has been cooperative across both canaries.

Structurally, PR-11 is **the test of orthogonality**: if the
v3 framework is correctly factored, OnAgent (PR-10) and
OnBehalfOf (PR-11) compose with zero shared state and zero
cross-axis bleed. The Risk register flags this directly.

## 10. Risk register (PR-11-scoped)

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| `with_on_behalf_of` body's drive loop accidentally reads the worker's own task identity | Low | High | SUBJ-1 enforced by absence of a `current_thread_identity()` accessor; all authority lookups go through `&SubjectContext`. Pinned by a test asserting `subject.thread().is_none()` inside the body. |
| Owner's authority drifts during the borrow (`setuid` mid-borrow) — borrow sees stale cred | Low | Low | **By design** per `06_EXECUTION_SCOPE_v1.md` §4: snapshot semantics, stable for borrow duration. v1 does not aim for mid-borrow authority refresh. Test pins the property. |
| Worker's `copy_to_user` writes to the wrong address space (worker's, not P's) | Medium | High | The borrow's `SubjectContext.process` is P's `Cap<ProcessIdentity>`; all user-memory access resolves through `subject.process().aspace_cap()`. SUBJ-2(b) + the absence of a "current address space" thread-local enforce. Test exercises a cross-aspace write under borrow. |
| Worker's exit_source subscription races with `io_destroy` | Low | Medium | `06_EXECUTION_SCOPE_v1.md` §5 + DTOK-3 race-determinism pattern from PR-7: the source fires, the drive loop's next yield-resolution observes `Killed`, the body returns. Test exercises the race. |
| Completion ring write-back interleaves badly across multiple in-flight iocbs | Medium | Medium | Worker is a *single* task processing iocbs from its queue sequentially; in-flight count is 1 in the canary. Concurrent worker pool deferred to PR-11.2. |
| AIO's fd-shape divergence from Linux (`io_setup` returns fd, not `aio_context_t` pointer) breaks userspace AIO libraries | Medium | Low | Acknowledged divergence; the AIO test harness uses our shape directly. Linux-bug-for-bug compatibility is not a v3 goal. Glibc shim is a 5-line bridge. |
| Borrow scope held too long → owner exit takes longer to release scope-held resources | Low | Low | `06_EXECUTION_SCOPE_v1.md` §6: scope-bound `OperationalEvidence` discipline. The canary's only scope-bound resource is the `Cap<ProcessIdentity>` itself; drop is one slot retire. |

The highest-impact risk is the **cross-aspect read of the
worker's identity** — the SUBJ-1 hygiene. PR-11 stands or falls
on whether the `&SubjectContext` discipline holds across the
worker's body. The test pinning this is non-negotiable.

## 11. Success criteria for PR-11

PR-11 is "done" when:

- A Rust integration test (`v3_aio_e2e.rs`) opens a file in P,
  calls `io_setup`, submits a `PREAD` iocb, calls
  `io_getevents`, retrieves the completion, and observes the
  expected buffer contents.
- A second test exercises `io_destroy` (or P-exit) mid-flight
  and asserts the worker task aborts cleanly.
- A third test asserts authority-snapshot semantics: P does a
  `setuid` mid-flight; the in-flight iocb is checked against the
  pre-setuid cred (or the test exercises the alternative
  documented v1 behavior — snapshot-at-borrow-time).
- The `sys_io_setup` / `sys_io_submit` / `sys_io_getevents` /
  `sys_io_destroy` syscall surface is reachable from the Linux
  syscall shim with no compile-time gating.
- `06_EXECUTION_SCOPE_v1.md` §12 migration table is updated to
  reflect AIO as landed.
- `07_BLAST_RADIUS.md` §5.2 PR-11 row is marked landed.

## 13. Future canaries (informational)

Once the `OnBehalfOf<P>` framework lands in PR-11, the natural
second canary is **io_uring SQPOLL** — a kthread that polls a
user-mmapped SQ ring and submits work under the owning process's
borrow. The shape is identical: one reactor task per ring, one
`with_on_behalf_of` borrow at startup, per-SQE sub-scripts inside
the borrow (`06_EXECUTION_SCOPE_v1.md` §8.1 worked example). The
substrate work is fully reused — io_uring adds its own iocb
shape (an SQE), its own completion ring (the CQE ring), and
registered-buffer machinery, but no further `OnBehalfOf` work.
A future PR-12 / PR-13 ships io_uring on top.

Other listed users (FUSE helper, cgroup writeback) are
informational — they each consume the same framework with their
own subsystem-side work. None require additional `OnBehalfOf`
framework changes.
