# Wait/Wake 机制导读 —— 这套东西是什么、网络栈为什么需要它、两套怎么合

<!-- txdoc:07-NET-WAIT-PRIMER-V1 -->

> 配套 [`WAIT_STAGE2_v1.md`](WAIT_STAGE2_v1.md)（技术方案，密）。**本文只讲概念、不讲代码**，用一个 `recv()` 的例子贯穿，回答四件事：① 这套东西是干什么的；② 网络栈为什么离不开它；③ 你内核里的两套各管什么；④ 合并（拆一套补到另一套）会遇到什么、怎么装。

---

## 1. 这套东西是干什么的？——「睡觉 / 叫醒」

一句话：**让一个在等条件的任务先去睡（不占 CPU），等条件真满足的那一刻被准确叫醒。**

Linux 里管这叫「等待队列（wait queue）」。你的内核里就是这套 wait/wake 机制。

拿一个最常见的场景走一遍 —— 程序调用 `recv()` 想从一个 socket 读数据，但数据还没到：

```
   ┌─────────────────────────────────────────────────────────┐
   │  ① recv(socket)：想读，但 socket 里现在没数据             │
   └───────────────────────────┬─────────────────────────────┘
                               ▼
   ┌─────────────────────────────────────────────────────────┐
   │  ② 任务去睡（让出 CPU），临走登记一句：                    │
   │     「等 socket#7 变成可读了，叫我一声」                    │
   └───────────────────────────┬─────────────────────────────┘
                               │     … 任务睡着，CPU 先去干别的活 …
                               ▼
   ┌─────────────────────────────────────────────────────────┐
   │  ③ 过一会儿网卡收到包 →「socket#7 可读了！」→ 去通知登记簿  │
   └───────────────────────────┬─────────────────────────────┘
                               ▼
   ┌─────────────────────────────────────────────────────────┐
   │  ④ 登记簿翻出「谁在等 socket#7」→ 把唤醒投进那个任务的信箱  │
   │     → 任务醒来 → 重跑 recv → 这次拿到数据                   │
   └─────────────────────────────────────────────────────────┘
```

整套东西就干这四步里的 ②③④：**登记「等谁」、事件来了「找到等的人」、把唤醒「投进信箱」。** 就这么简单一件事——但它是所有阻塞式系统调用的地基。

---

## 2. 网络栈为什么离不开它？

因为**网络本质是异步的**：一个包什么时候到、一个连接什么时候握手完成，内核事先完全不知道——它们由**网卡中断**或**后台网络任务（delegate）**在不确定的时刻送达。

于是每一个会「卡住等」的网络操作，背后都是这套 wait/wake：

| 网络操作 | 在等什么条件 |
|---|---|
| `recv` / `read` | socket 变成可读（有数据来了） |
| `send` / `write` | socket 变成可写（发送缓冲有空了） |
| `accept` | 有新连接进来 |
| `connect` | 对端握手完成 |
| `poll`/`select`/`epoll` | 上面这些里的**任意一个**就绪 |

做错只有两种下场，都很致命：
- **忙等**（不睡、原地空转着反复查）→ 烧满 CPU，别的活干不了；
- **丢唤醒**（睡了、但事件来时没找到你 / 没叫你）→ **永久挂死**，程序卡住不动。

> 这正是网络栈审计里那句「net 和别人不一样」的由来：内核有 8 个文件描述符子系统（eventfd/timerfd/signalfd…）早就搬到了**新那套** wait/wake，唯独 socket 的阻塞路径一直停在**老那套**。Stage 1（已完成）把 socket 的 recv/send/accept/connect 搬了过去；剩下的收尾就是本文要讲的「两套合并」。

## 3. 你的内核里有两套「叫醒登记簿」

这就是你说的「两套东西」。它们**干的是同一件事**（登记谁在等、事件来了叫醒谁），只是中间那层实现不同。用上面的图来对照：

```
        老那套（现状）                     新那套（目标）
   ┌──────────────────────┐          ┌──────────────────────┐
   │ poll / select        │          │ epoll · socket 阻塞   │   ← 谁在等（消费者）
   └──────────┬───────────┘          └──────────┬───────────┘
              │ 用 wait_on_token 查             │ 用 await_wait_source 查
              ▼                                 ▼
   ┌──────────────────────┐          ┌──────────────────────┐
   │ 子系统登记簿          │          │ substrate 登记簿      │   ← 两本不同的登记簿
   └──────────┬───────────┘          └──────────┬───────────┘
              ▼                                 ▼
   ┌──────────────────────┐          ┌──────────────────────┐
   │ Channel / RawQueue    │          │ WaitSource（防丢唤醒）│   ← 唤醒的载体
   └──────────┬───────────┘          └──────────┬───────────┘
              └───────────────┬─────────────────┘
                              ▼
                 ┌──────────────────────────┐
                 │     任务信箱 Mailbox      │   ← 关键：两套最终都投这里！
                 └──────────────────────────┘
```

**两套各管什么：**

| | 老那套（A） | 新那套（B，目标） |
|---|---|---|
| 谁在用它 | `poll` / `select`；历史上的 socket 阻塞 | `epoll`；eventfd/timerfd/signalfd… 8 个子系统；Stage 1 后的 socket |
| 门票（怎么指认「等谁」） | `WaitToken` | `WaitSourceId` |
| 查哪本登记簿 | 子系统登记簿 | substrate 登记簿 |
| 消费函数（去睡的入口） | `wait_on_token` | `await_wait_source` |
| 唤醒载体 | `Channel` / `RawQueue` | `WaitSource`（**多一个「防丢唤醒」暂存格**） |

**最关键的一点**：两套**底层是同一个任务信箱（Mailbox）**。分叉只发生在中间那层（登记簿 / 门票 / 消费函数）。正因为底座相同，两套才**能**合并——否则根本合不了。

新那套为什么更好？它的载体 `WaitSource` 多了一个**「防丢唤醒」暂存格**：万一「叫醒」比「登记」早到了一步（并发下很常见），暂存格会把这次唤醒记下来，等你登记的瞬间补给你。老那套没有这个保险，理论上会漏。所以合并的方向是「**留新、退老**」。

## 4. 现在是「共存期」：一件事登记两次、通知两次

你现在看到「有两套」，是因为迁移做到一半、停在一个**过渡态**：11 个子系统目前**双注册**——同一个 id 在两本登记簿里都登记，事件发生时**两边都通知**。这样不管消费者用的是老的还是新的，都能被叫醒，互不影响。

```
现在（共存期）：一个「socket#7 可读」事件发生
                       │
           ┌───────────┴───────────┐
           ▼                       ▼
     通知老登记簿              通知新登记簿
   （让 poll/select 醒）    （让 epoll / socket阻塞 醒）

─────────────────────  合并后  ─────────────────────

目标（终态）：一个「socket#7 可读」事件发生
                       │
                       ▼
                只通知新登记簿
          （所有等的人都从这一本醒）
```

**合并 = 把所有「等的人」都搬到新那套，然后把老登记簿、老通知整个删掉，只剩新那套那一条线。**

## 5. 合并（拆老补新）会遇到哪些问题？

四个坑，按危险程度排：

1. **顺序坑（最致命）。** 必须**先**把所有等的人搬到新那套，**再**删老通知。反了——有人还蹲在老登记簿等、而老通知已经被你删了——就**永远没人叫他，挂死**。而且这种错**编译器查不出来**（代码编译得过，运行才卡），只能靠严格的顺序纪律 + 每步跑一下真机验证。

2. **tty 坑（最可能暴雷的具体点）。** tty（终端）的**新**登记簿其实**从来没被真正用过**——因为 `epoll` 不支持 tty，而 socket 阻塞又不涉及 tty。等 `poll` 一迁到新那套，会是 tty 新路径的**首次真用**。首次真用最容易暴露潜伏问题。所以这一步要**单独**拿 tty 测一遍，别混在一批里蒙混过关。

3. **够不着坑。** 有两个「等的人」住在**下层**（网络的后台泵任务、内存的范围锁），它们在代码分层上**够不着**上层那个新消费函数 `await_wait_source`。→ 得给它们各补一个**约 30 行的小助手**：自己带一个信箱、直接在新登记簿上登记、睡、等叫醒。不难，但属于「新增基建」，得单独做。

4. **认错承重墙坑。** `reactor Channel` 看着像是老那套的一部分（老载体之一），**其实它还扛着另一份完全无关的活**：定时器超时等待、完成量（Completion）这些。它们跟「网络就绪」没关系，但会用到 `Channel`。→ **千万别把 `Channel` 删了。** 合并要删的是「**子系统登记簿那本 + 老通知**」，不是 `Channel` 这个类型本身。（这是原技术方案里最容易被误解、也最需要纠正的一条。）

## 6. 怎么把老那套的东西「装」到新那套上？

好消息：因为「双注册」早就把**每个 id 都在新登记簿登好了**，所以「装」的**大半工作其实已经做完**。剩下的就是把消费者的查询改向、补两个小助手、再撕掉旧的。三步：

**第一步：把消费者改成查新登记簿。**
上层的 `poll` / `select` / `sigtimedwait` 直接改成调新那个 `await`——因为**门票的 id 数字两套是一样的**（双注册时就是拿同一个 id 登两本），改个查询入口就能直接用，现成的 `epoll` 就是照抄的模板。

**第二步：给够不着的两个下层消费者补小助手。**
就是第 5 节坑 3 那两个（网络后台泵、内存范围锁），各补一个约 30 行、自带信箱的小助手，让它们能直接在新登记簿上登记等待。

**第三步：撕掉生产者的老半边。**
每个子系统把「往老登记簿登记」和「通知老登记簿」这两处删掉，只留「通知新登记簿」。**这一步必须在第一、二步全做完之后做**（否则触发坑 1）。最后把整本老登记簿（`wait_source.rs` 那套）删掉，合并完成。

**安全顺序**（每步都能单独验证、单独回退，详见 `WAIT_STAGE2_v1.md`）：

```
补小助手基建 → 删死代码 → 迁上层消费者(poll/select…) → 迁下层消费者(泵/锁)
            → 逐个子系统撕老半边 → 删掉整本老登记簿
   ↑先搬人                                        ↑后撕旧（坑1的铁律）
```

---

## 7. 一句话总结

你有**两本「叫醒登记簿」在干同一件事**；它们共用同一个任务信箱，只是中间那层不同；新那本更安全（多了「防丢唤醒」暂存格）。**合并 = 让所有等的人都改查新那本，再撕掉旧那本**——难点不在「撕」，而在**撕的顺序**（必须先搬人、后撕旧，否则静默挂死），以及**别误撕了其实在扛定时器的 `Channel`**。而这套东西对网络栈的意义是：**没有它，每一个 `recv`/`accept`/`poll` 要么烧 CPU 空转、要么丢唤醒卡死**——它是所有阻塞式网络操作能正确「睡下去、又醒过来」的地基。
